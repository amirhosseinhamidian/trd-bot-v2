# P6-05 — راهنمای نصب تازه و مهاجرت v0.2 به v0.3

وضعیت: **راهنمای آماده اجرا؛ شواهد اجرای واقعی در P6-06 ثبت می‌شوند**

این راهنما مسیر پشتیبانی‌شده برای رسیدن از baseline محلی v0.2.0 به release candidate محلی
v0.3.0 را تعریف می‌کند. v0.3 یک لایه افزایشی روی v0.2 است، نه بازنویسی سامانه. داده‌های
پژوهشی، lineage و journalهای immutable باید حفظ شوند و read modelهای قابل بازسازی نباید جای
evidence اصلی را بگیرند.

## قرارداد نسخه و محدوده

| مورد | مبدأ | مقصد |
| --- | --- | --- |
| نسخه | `0.2.0` | `0.3.0` |
| Git | tag `v0.2.0` / commit `6e101f9f66ba83720335077f409b53d012cdbf5c` | candidate SHA که بعداً Freeze می‌شود |
| Alembic | `20260926_0017` | `20261020_0036` |
| PostgreSQL | 17 | 17 |
| حالت‌ها | `RESEARCH`, `BACKTEST`, `PAPER`, `SHADOW` | بدون تغییر |

این فرایند فقط برای نصب محلی تک‌کاربره و داده عمومی بازار است. اتصال حساب صرافی، API key یا
secret صرافی، ارسال/لغو سفارش، کیف پول، انتقال وجه، Live Execution و مدیریت دارایی واقعی بخشی
از این release نیستند.

## انتخاب مسیر

- برای مخزن و دیتابیس خالی از بخش «نصب تازه» استفاده کنید.
- برای دیتابیس موجود v0.2 فقط از بخش «ارتقای درجا» استفاده کنید.
- اگر `alembic current` دقیقاً `20260926_0017` نیست، ارتقای v0.3 را شروع نکنید. ابتدا با کد
  همان نسخه قدیمی، دیتابیس را به head رسمی v0.2 برسانید یا یک restore تأییدشده انجام دهید.
- روی دیتابیس دارای داده هرگز چرخه CI یعنی `alembic downgrade base` را اجرا نکنید. آن چرخه فقط
  برای دیتابیس موقت و قابل حذف است.

## ارتقای درجا از v0.2.0

### 1. preflight و توقف writerها

API، worker و frontend را متوقف کنید، ولی PostgreSQL را روشن نگه دارید. سپس وضعیت را ثبت کنید:

```bash
git status --short
git rev-parse HEAD
python -m alembic current
docker compose ps
```

شرایط عبور:

- worktree باید clean باشد؛
- SHA مبدأ باید ثبت شود؛
- خروجی Alembic باید `20260926_0017` باشد؛
- هیچ worker یا API نباید هنگام backup و migration روی دیتابیس بنویسد.

### 2. backup خارج از repository

مسیر backup باید absolute، خارج از repository و دارای دسترسی محدود باشد. فایل `.env` ممکن است
credential دیتابیس محلی داشته باشد؛ آن را commit نکنید.

```bash
export TRD_BOT_BACKUP_DIR="/absolute/path/outside/repository/trd-bot-v0.2-backup"
mkdir -p "$TRD_BOT_BACKUP_DIR"
chmod 700 "$TRD_BOT_BACKUP_DIR"

docker compose exec -T postgres pg_dump -U trd_bot -d trd_bot \
  --format=custom --no-owner --no-acl \
  > "$TRD_BOT_BACKUP_DIR/trd_bot_v0_2.dump"
docker compose exec -T postgres pg_dump -U trd_bot -d trd_bot \
  --schema-only --no-owner --no-acl \
  > "$TRD_BOT_BACKUP_DIR/trd_bot_v0_2_schema.sql"
cp .env "$TRD_BOT_BACKUP_DIR/env.backup"
chmod 600 "$TRD_BOT_BACKUP_DIR/env.backup"
shasum -a 256 "$TRD_BOT_BACKUP_DIR/trd_bot_v0_2.dump" \
  "$TRD_BOT_BACKUP_DIR/trd_bot_v0_2_schema.sql" \
  > "$TRD_BOT_BACKUP_DIR/SHA256SUMS"
```

حداقل baseline داده را نیز ثبت کنید:

```bash
docker compose exec -T postgres psql -U trd_bot -d trd_bot -v ON_ERROR_STOP=1 -c \
  "SELECT 'dataset_snapshots' AS relation, count(*) FROM dataset_snapshots
   UNION ALL SELECT 'research_experiments', count(*) FROM research_experiments
   UNION ALL SELECT 'simulated_portfolios', count(*) FROM simulated_portfolios
   UNION ALL SELECT 'simulated_positions', count(*) FROM simulated_positions
   UNION ALL SELECT 'candidate_journals', count(*) FROM candidate_journals;" \
  > "$TRD_BOT_BACKUP_DIR/v0_2_row_counts.txt"
```

قبل از ادامه، restore را روی دیتابیس disposable مستقل آزمایش کنید؛ نام زیر نباید نام دیتابیس dev
یا test فعال باشد:

```bash
docker compose exec -T postgres dropdb --if-exists -U trd_bot trd_bot_restore_drill
docker compose exec -T postgres createdb -U trd_bot -O trd_bot trd_bot_restore_drill
docker compose exec -T postgres pg_restore -U trd_bot -d trd_bot_restore_drill \
  --no-owner --no-acl < "$TRD_BOT_BACKUP_DIR/trd_bot_v0_2.dump"
docker compose exec -T postgres psql -U trd_bot -d trd_bot_restore_drill \
  -v ON_ERROR_STOP=1 -c "SELECT version_num FROM alembic_version;"
```

دیتابیس drill را فقط پس از ثبت نتیجه حذف کنید. دیتابیس اصلی را برای آزمون restore بازنویسی نکنید.

### 3. دریافت کد candidate و dependencies

Candidate SHA موردنظر را صریح checkout کنید و SHA را دوباره ثبت کنید. فایل `.env` موجود را حفظ
کنید و آن را با `.env.example` جایگزین نکنید.

```bash
git fetch --tags origin
git checkout <candidate-sha>

python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -e ".[dev]"

cd frontend
npm ci
cd ..
```

در `.env` مقدار `TRD_BOT_APP_VERSION=0.3.0` را تنظیم و مقصدهای
`TRD_BOT_DATABASE_URL` و `TRD_BOT_TEST_DATABASE_URL` را بررسی کنید. secret جدیدی برای market
provider لازم نیست. frontend در صورت نیاز فقط از `NEXT_PUBLIC_API_BASE_URL` عمومی استفاده می‌کند.

### 4. اجرای migration

```bash
python -m alembic current
python -m alembic upgrade head
python -m alembic current
python -m alembic check
```

خروجی نهایی باید `20261020_0036 (head)` و «No new upgrade operations detected» باشد. زنجیره
0018 تا 0036 به‌ترتیب dataset staging، market event/retention، Market Context، Alerting و Decision
Intelligence را اضافه می‌کند. migration نباید journalهای v0.2 را پاک کند یا retention cleanup را
خودکار اجرا کند.

اگر migration شکست خورد، همان command را کورکورانه تکرار نکنید. writerها را خاموش نگه دارید،
خطا و revision فعلی را ثبت کنید و از backup تأییدشده برای ساخت دیتابیس جایگزین استفاده کنید.

### 5. تغییرات سازگاری API

شش mutation هم‌زمان legacy عمداً `410 Gone` می‌دهند. client باید endpoint durable جایگزین را
فراخوانی و وضعیت execution را poll کند.

| endpoint بازنشسته | جایگزین durable |
| --- | --- |
| `POST /api/v1/research/ema-crossover` | `POST /api/v1/research/experiment-executions` |
| `POST /api/v1/research/experiments/ema-crossover` | `POST /api/v1/research/experiment-executions` |
| `POST /api/v1/research/experiments/ema-crossover/from-dataset` | `POST /api/v1/research/experiment-executions` |
| `POST /api/v1/research/walk-forward/ema-crossover` | `POST /api/v1/research/walk-forward-executions` |
| `POST /api/v1/research/walk-forward/runs/ema-crossover` | `POST /api/v1/research/walk-forward-executions` |
| `POST /api/v1/research/walk-forward/runs/ema-crossover/from-dataset` | `POST /api/v1/research/walk-forward-executions` |

پاسخ 410 دارای `Deprecation`، `Sunset` و `Link` است. جزئیات قرارداد در
[`08-retire-synchronous-research-routes.md`](08-retire-synchronous-research-routes.md) آمده است.

برای frontend، facadeهای `@/lib/api/client`، `@/lib/api/types` و
`@/lib/api/portfolio-analytics` بازنشسته‌اند. importها باید به client/type همان feature یا
`src/lib/api/core` منتقل شوند. نقشه کامل در
[`../nexora-ui-release-and-migration.md`](../nexora-ui-release-and-migration.md) ثبت شده است.

### 6. verification پس از ارتقا

ابتدا قرارداد release و مستندات را اجرا کنید:

```bash

```

سپس تمام gateها:

```bash
python -m ruff format --check .

python -m mypy

python -m alembic check
python -m pytest -m integration -q

cd frontend
npm run format:check
npm run lint
npm run typecheck
npm run test -- --run
npm run build
cd ..
```

API و worker را جداگانه راه‌اندازی کنید:

```bash
python -m uvicorn trd_bot.main:app --reload

```

موارد دستی الزامی:

- health نسخه `0.3.0` را نشان دهد؛
- row countهای baseline کم نشده باشند؛
- lineage از Dataset تا Experiment/Context/Candidate/Decision/Portfolio قابل دنبال‌کردن باشد؛
- durable job پس از restart/reclaim تکراری نسازد؛
- UI در locale فارسی و انگلیسی و theme روشن/تیره باز شود؛
- هیچ credential صرافی، private-account route یا live-order capability وجود نداشته باشد؛
- برنامه retention ابتدا به‌صورت dry-run بررسی شود؛ cleanup خودکار مجاز نیست.

## rollback عملیاتی

Alembic downgrade راه rollback داده واقعی نیست. اگر post-upgrade verification شکست خورد:

1. API، worker و frontend v0.3 را متوقف کنید.
2. دیتابیس ناموفق v0.3 را برای بررسی حفظ و read-only کنید؛ آن را پاک یا روی آن restore نکنید.
3. یک دیتابیس جایگزین خالی بسازید و dump تأییدشده v0.2 را با `pg_restore` در آن بازیابی کنید.
4. tag `v0.2.0` را checkout و dependencies همان نسخه را نصب کنید.
5. URL دیتابیس را به دیتابیس بازیابی‌شده تغییر دهید و `alembic current`، health و row countها را
   بررسی کنید.
6. فقط پس از تأیید شواهد، writerهای v0.2 را دوباره فعال کنید.

هرگز `python -m alembic downgrade base`، `docker compose down -v` یا حذف volume را روی دیتابیس
دارای داده اجرا نکنید.

## نصب تازه v0.3

برای محیط خالی:

```bash
git checkout <candidate-sha>
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -e ".[dev]"
cp .env.example .env
docker compose up -d postgres
python -m alembic upgrade head
python -m alembic current
python -m alembic check

cd frontend
npm ci
npm run build
cd ..
```

انتظار می‌رود دیتابیس خالی روی `20261020_0036 (head)` قرار گیرد. seedهای demo اختیاری و
read-only هستند؛ برای تأیید fresh install به داده واقعی یا credential خصوصی نیاز نیست.

## الگوی evidence برای P6-06

حداقل موارد زیر باید به candidate SHA متصل و بدون secret ثبت شوند:

- source SHA/tag/revision و target SHA/revision؛
- checksum dump و نتیجه restore drill؛
- row countهای قبل و بعد؛
- خروجی migration current/check؛
- نتیجه gateهای backend، PostgreSQL و frontend؛
- نتیجه smokeهای API/UI/worker و no-live security؛
- تصمیم نهایی `PASS` یا `FAIL` و دلیل هر failure.

این سند به‌تنهایی Freeze یا انتشار نیست. Freeze نهایی فقط پس از fresh-install و upgrade evidence،
CI سبز روی همان SHA و acceptance record معتبر انجام می‌شود.
